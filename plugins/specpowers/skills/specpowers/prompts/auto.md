# auto.md — 全流程无人值守契约

## 触发与参数

当用户调用 `/specpowers-auto "<设计文档路径>"` 时加载本契约。

**参数**：唯一参数 = 设计文档路径。方案名、修改范围表、场景清单、降级策略、硬边界等信息**不作为命令参数**，由 agent 开工前从该文档解析（见「八要素文档解析清单」）。

> **定位**：元编排模式——与 `/specpowers-fast`（判小跳阶段）对偶，`auto` 六阶段全走但无人值守直通。
> 本契约不新增流水线阶段、不改状态机语义；codex-review 不是 specpowers 阶段，而是 build 与 archive 之间编排的外部技能（插件内零副本）。
> **feature 说明**：路径中的 <feature> 来自 state.json 的 feature 字段，与人工模式一致。

## 无人值守总原则

全程无人工介入：所有需要决策的点基于**设计文档与代码事实**自行决策并继续推进。各阶段出现的确认或卡转人工节点（含 build 执行方式确认、门禁「转人工」信号）一律按下方「裁决规则表」自行裁决后继续，**不等待用户输入**；仅当出现「硬阻断」时才停下并报告原因。

## 前置校验（第 0 步）

```bash
python -m specpowers_cli.bridge.facade status --root .
```

- 确认依赖就绪（OpenSpec CLI、superpowers；缺失的处理见各阶段既有规则）
- 校验设计文档存在：`<设计文档路径>` 文件不存在 → 这是参数错误，属硬阻断（无法从文档恢复），停下报告
- 检测 codex-review 技能可用性：
  - 可用 → 第 6 步按 6a–6d 编排执行
  - 不可用 → **降级不阻断**：第 6 步改用本契约内置最小自审 checklist（见 6b 末尾），并在汇总报告中标注「本次为降级审查」

### 基点记录

记录当前 HEAD 提交号（作为后续 codex-review 的改动基点），写入 `.specpowers/auto_base.json`：

```json
{
  "base_commit": "<HEAD SHA>",
  "design_doc": "<设计文档路径>",
  "created_at": "<ISO 时间>",
  "parsed": { "八要素解析结果，见下节" }
}
```

写入方式沿用 `core/fs_state.py` 的原子写（临时文件 + rename），与 state.json 一致。

### 八要素文档解析清单

开工前从设计文档解析以下八要素，解析结果随基点一并落盘到 `auto_base.json` 的 `parsed` 字段，供后续各阶段直接引用（兼防长流程上下文压缩丢失）：

| # | 要素 | 用途 |
|---|------|------|
| 1 | 功能名 | feature slug、各阶段标题 |
| 2 | 已定方案 | brainstorm 跳过方案取舍的直接依据；文档必须已定稿方案，否则按裁决规则表处理 |
| 3 | 核心调用链 | brainstorm 核对代码事实的范围（关键类/服务/Controller 清单） |
| 4 | 必测场景清单 | specify 的场景来源（逐条列出） |
| 5 | 修改范围表 | plan 的任务拆分依据（改 N 处文件清单 + 新增文件/DTO/枚举清单） |
| 6 | 编码约束 | build 的编码要求（通常指向仓库 AGENTS.md + 文档内特殊约束） |
| 7 | 外部依赖降级策略 | build 阶段未就绪外部接口的处理方式（如 Remote 降级：返回空 + warn 日志 + 完整异常堆栈） |
| 8 | 硬性边界 | 全程红线（如不改表结构、不新增枚举值、不新增第三方依赖、修复不扩范围） |

解析不到某要素时：先在文档中二次检索（换关键词/看章节标题）；仍无 → 该要素按裁决规则表「文档无结论」处理并在落盘时标注 `null` + 原因。

## 阶段编排表（0–7）

按序执行，每个阶段产物落盘并通过该校验后再进入下一阶段：

| 步 | 动作 | 无人值守覆盖点 |
|----|------|----------------|
| 0 | 前置校验 + HEAD 基点 + 八要素解析落盘 | — |
| 1 | `/specpowers-constitution` | **幂等执行**（无论是否已存在都执行，确保状态机推进到 ready）；原则内容从仓库 AGENTS.md 提取编码约束自动填充，不等待用户输入 |
| 2 | `/specpowers-brainstorm "<基于 <设计文档> 实现 <功能名>（<方案名>）>"` | 技术方案已在文档定稿 → **跳过方案取舍确认**，探索仅用于核对八要素「核心调用链」的现有代码事实；proposal.md 的「数据流契约」小节按文档对应章节填写；文档已定全流程 → 拒绝判小 |
| 3 | `/specpowers-specify "<基于 proposal.md 与设计文档生成 <功能名> 功能规格>"` | 场景清单直接取自八要素「必测场景清单」，逐条覆盖，缺一不可 |
| 4 | `/specpowers-plan` | 任务拆分严格对照八要素「修改范围表」，每个任务标注涉及文件路径与验收要点 |
| 5 | `/specpowers-build` | 执行方式按 tasks.md 顶部推荐自行确认（默认 conductor 顺序执行）；实时门禁三态与 TDD 照常遵守；「转人工」信号按裁决规则表处理 |
| 6 | codex-review 编排 | 见下节 6a–6d |
| 7 | `/specpowers-archive` | 归档校验报告问题 → 按「只转人工、不打回」机制记录问题后正常收尾，**不重做前序阶段** |

各阶段调用方式与人工模式完全一致（先调 facade 确定性层，再按对应 `prompts/<stage>.md` 契约执行认知任务）。

## 裁决规则表（无人值守核心）

各阶段既有契约中要求用户交互的节点，统一按此表裁决：

| 交互节点类型 | 自动裁决策略 | 记录要求 |
|--------------|--------------|----------|
| 方案/选项确认（文档已有结论） | 按文档结论执行 | 日志注明文档出处章节 |
| 方案确认（文档无结论） | 选保守/默认项（影响面小、可回退的选项） | 记录备选项与选择理由 |
| build 门禁「转人工」信号 | 可自愈（改代码/补测试/重编译可解决）→ 自愈后继续；不可自愈 → 按硬阻断处理 | 记录信号内容与处置结果 |
| 判小/升级确认（误入 fast 判定逻辑） | 文档已定全流程 → 拒绝判小，走完整流水线 | — |
| 执行方式确认（conductor/subagent） | 按 tasks.md 顶部推荐，无推荐则默认 conductor 顺序执行 | — |
| 需求歧义/多种合理理解 | 回设计文档找依据；文档无依据 → 选不改变现有行为的理解 | 记录歧义点与采信依据 |
| 未列出的交互节点 | **一律选默认项 + 记录后继续（兜底条款）** | 记录节点内容与所选默认项 |

裁决日志随汇总报告输出（可追加写到 `.specpowers/auto_base.json` 同级的 `auto_decisions.md`），保证「裁决 + 留痕」可审计。

## 第 6 步：codex-review 编排（外部技能，插件内零副本）

codex-review 是用户级外部技能，本契约只做三件事：**传基点、滤范围、控迭代**。审查机制（上下文收集脚本、完整方法体提取、多 Pass、P1/P2 分级）全部由技能自带，本契约不重建。

### 6a. 范围准备

1. 读取 `.specpowers/auto_base.json` 的 `base_commit`
2. 确定审查范围 = **基点之后的新增提交 + 工作区未提交改动**（已暂存 + 未暂存 + 未跟踪），仅限本次功能产生的改动
3. 按八要素「修改范围表」过滤变更文件清单，生成交给审查的 diff 输入

### 6b. 调用 codex-review 技能

通过 Skill 工具调用 codex-review 技能，按其 SKILL.md 工作流执行：

- 上下文收集：以基点 SHA 作为 `--base` 传给 `gather_review_context.py`；若脚本当前版本仅支持分支名，**回退**为手动 `git diff <base>..HEAD` + 工作区 diff 收集后再进入审查
- 变更 > 30 文件或包含 3 层以上嵌套条件的方法 → **必须启用 `--extract-methods`**（完整方法体提取）
- Pass 1（模式匹配）、Pass 2（控制流追踪）必须执行；diff 涉及 DTO 新增字段 / 新枚举 + 服务层按值过滤 → **自动触发 Pass 4 跨文件数据流追踪**（入口 → 服务层 → 缓存 → SQL 逐环节范围一致性）
- 输出要求：中文、`[P1]`/`[P2]` 严重度标签、含各 Pass 发现与自检清单填写结果

**降级审查（codex-review 不可用时）**：改用最小自审 checklist——① 完整方法体核对（多层嵌套/多 return 方法禁止只看 diff 片段）；② 新增 DTO 字段/枚举的跨文件消费链路核对；③ 对照八要素「必测场景清单」逐条确认实现存在；④ 对照「硬性边界」逐条确认未越界；⑤ 编译验证。结果同样以 `[P1]`/`[P2]` 标注。

### 6c. 修复策略

- **仅修复「本次改动引入」的问题**：P1/P2 逐一修复，保持既有代码风格，修复后重新编译验证
- 非本次改动引入的历史问题：**只记录不修改**
- 修复不得扩大改动范围，仅限 6a 变更清单内的本次功能相关文件；每轮复审前重新核对清单

### 6d. 迭代控制：最多 2 轮

- 轮次上限默认 **2**（本契约内可配置），每轮 = 复审 + 修复 + 重编译
- 每轮通过条件：无本次改动引入的 P1/P2 遗留
- 2 轮后仍有遗留 blocking 问题 → 记入汇总「遗留风险」交人工裁决；若已导致编译不过 → 按硬阻断停下

> 设计依据：两轮构成「发现 → 修复 → 验证」的最小完整闭环。第 3 轮起边际收益趋零（剩余多为设计层问题，同一审查者-修复者继续迭代不产生新信息）；硬上限防止无人值守下「修复引入新问题」的振荡不收敛，并限定 review 对整条流水线的资源占用。

### 接口假设（上游变更时需同步本契约）

本契约对 codex-review 的耦合面仅四处，上游技能变更以下任一项时需同步修订本节：

1. 技能名 `codex-review`（Skill 工具调用目标）
2. 脚本 `gather_review_context.py` 及 `--base` / `--extract-methods` 参数
3. 输出严重度标签 `[P1]` / `[P2]`（6c 修复策略的过滤依据）
4. 中文输出约定（汇总报告可读性约定）

## 硬阻断定义（唯一允许停下的情形）

| 类型 | 示例 |
|------|------|
| 外部强依赖不可用且无降级 | OpenSpec CLI 缺失导致 archive 拒绝执行且无法安装；编译环境不可用 |
| 状态机不一致无法自愈 | facade 报非法 stage 跃迁且 reset 也无法恢复 |
| 设计文档自相矛盾无法裁决 | 同一需求点两处结论冲突且无法判定权威章节 |
| 参数错误 | 设计文档路径不存在 |

停下时必须输出：① 阻断原因；② 已完成阶段；③ 各产物位置；④ 恢复方式（**重入 `/specpowers-auto` 即续跑**）。

## 中断续跑

重入 `/specpowers-auto` 时：

1. 读 `.specpowers/auto_base.json`（基点 + 八要素）——存在 → 本次是续跑，跳过第 0 步的重复解析；不存在 → 全新执行
2. 读 `state.json` 当前 stage + 各阶段产物存在性（constitution.md → proposal.md → spec.md → tasks.md → build 产物）定位断点
3. 从断点阶段继续，**已完成阶段不重做**

## 汇总输出

全部完成后（含正常收尾与硬阻断停下两种情况），按 `templates/auto-summary-template.md` 输出汇总报告，至少包含：各阶段产物路径、实际修改/新增文件清单、review 结论与修复清单、编译与测试结果、裁决日志摘要、遗留风险（外部依赖未就绪项、降级审查标注、2 轮后仍遗留问题）。
